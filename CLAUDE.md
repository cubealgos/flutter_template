# CLAUDE.md — flutter_template

A Flutter monorepo **template**, not a framework: each app clones this repo and then owns
its copy outright. There is no scaffolder and no upgrade channel — template fixes never
reach apps that already cloned. Apps are expected to drift apart after cloning.

## Read this before you do that

| about to… | read first |
| --- | --- |
| run any repo task | the `melos:` block in root `pubspec.yaml` (`gen`, `analyze`, `test`, `format`, `check-generated`, `gen-fresh-check`, `map`, `map-check`, `docs-check`, `changelog-check`, `icons`, `hooks`) |
| start work on an issue | Branches below — new worktree, never the main checkout |
| cut a release | `docs/releasing.md` — per-package `<pkg>-vX.Y.Z` tags, the security-gate checklist, the release PR template at `.github/PULL_REQUEST_TEMPLATE/release.md`; no required status checks configured by the template |
| add a new screen/feature | `fvm dart run tooling:new_feature <path>` (e.g. `settings/notifications`, parent folder must exist) — scaffolds view/controller/model/mobile layout, a view and a layout test, and the `TypedGoRoute` in `router.dart` (or prints the snippet if it can't edit safely); named after the last segment (`NotificationsView`, `NotificationsRoute`); refuses an existing path, `widgets`/`layouts`/`steps` and non-snake_case segments; then run `melos run gen` |
| add or change a screen's accessibility, or the axe check | `apps/app/README.md` "Accessibility on web" — `pumpScreen` asserts the `flutter_test` guidelines for every screen, `web_smoke` injects the vendored axe-core (`core/tooling/tooling/third_party/axe-core`, checksum in `web_smoke_axe.dart`) and fails on serious/critical violations; semantics are enabled in `apps/app/lib/main.dart`; every tappable control is >=48 dp |
| write a view or controller | `core/architecture/mvc` — the vendored `ViewModel`/`ViewController`/`ViewWidget` triad plus `NavigationService`/`LauncherService`/`DialogService`; views stay dumb, controllers navigate only through injected services; enforced by `core/architecture/mvc_lints`. Layout under `apps/app/lib/features/`: features **nest by route** (a screen whose route sits under another's is a sub-feature folder inside it), a feature root holds only its triad, feature-local types, the reserved folders `widgets/`/`layouts/`/`steps/` and sub-features; every helper widget lives in `widgets/` (one public widget per file, data and callbacks only, never the controller); **one view, up to three layouts**: `<f>_view.dart` is the feature's only `ViewWidget` (it owns the controller) and builds an `mvc` `ResponsiveLayout` over `layouts/<f>_mobile_layout.dart` (required) plus optional `<f>_tablet_layout.dart`/`<f>_desktop_layout.dart` (fallback desktop→tablet→mobile), each a dumb widget taking the model and callbacks — see `apps/app/README.md` "Feature structure", which also covers the i18n namespaces mirroring the feature tree (`settings.account`, `legal.licences`; parent labels `<target>Link`) |
| add/change a lint rule, threshold or doc requirement | root `analysis_options.yaml` (very_good_analysis, solid_lints) or `core/architecture/mvc_lints` (MVC rules) — both documented inline; an inline `// ignore:` for a plugin rule needs `plugin_name/rule_name`, not the bare rule name |
| write or change user-facing copy (i18n JSON, website text, email templates) | `tool/phrase-check.yaml` — the forbidden-phrase list (empty in the template; a clone in a regulated field fills it) plus keyed exceptions with exact sentence, reason and date; `melos run phrase-check` scans app and website copy plus the file's `sources:` and runs in CI |

| touch a generated file (`*.g.dart`, `*.freezed.dart`, `*.gr.dart`, `*.config.dart`, `*.mocks.dart`) | don't — regenerate via `melos run gen` instead; never hand-edit |
| touch the backend (schema, provisioning, deploy, or the Appwrite Cloud dev project) | `backend/appwrite/README.md` — `backend/appwrite/schema` declares the schema, `backend/appwrite/tool` (package `appwrite_tool`) provisions and deploys Functions and Sites — the dev backend is an Appwrite Cloud project (no local stack), configured in the gitignored `backend/appwrite/tool/.env.local`; production is a second gitignored `.env.production.local`, reached only with `--production` (`bin/promote.dart`, dry run first), and deployment never runs in CI — see `docs/releasing.md` "Deploying" |
| store rows that more than one person uses (an organisation's data), or add team membership, roles or invitations | `apps/app/README.md` "Teams and team-scoped rows" — **user-scoped rows** (`UserScope`, the default) are one person's own (settings, drafts, a profile), **team-scoped rows** (`TeamScope(teamId, readRoles:, writeRoles:)`) are shared by a team's members and follow membership at once; never invent tenancy in an adapter. `core/contracts/teams` holds the rules (`TeamEngine`: exactly one owner, ownership transfer, invitations, history), the `team_admin` action of `backend/appwrite/functions/api` runs them on Appwrite Teams — every membership change goes through it, and nobody is ever given Appwrite's native `owner` role |

| add a server-side operation (anything that needs a trusted backend) | `backend/appwrite/README.md` "Server-side operations: the `api` Function" — **never a new Function** (Appwrite Cloud's Free plan allows 2 per project; the schema test `maxFunctions` fails on a third): add an `ApiAction` under `backend/appwrite/functions/api/lib/src/actions/<name>/`, register it in `lib/src/registry.dart`, add its scopes to `api` in `backend/appwrite/schema` (`scopes_test.dart` enforces scopes = union of the actions'), and call it through `ApiClient` in `backend/appwrite/adapters`. `provision` deletes Functions the schema does not declare |

## Toolchain

Flutter 3.47.5 / Dart 3.13.4 via FVM — always run `fvm flutter ...` / `fvm dart ...` for the outer command. Inner melos-spawned commands resolve to the same pinned SDK via `sdkPath: .fvm/flutter_sdk`, no `fvm` prefix needed inside a script. **CI has no `.fvm/` checkout and must set `MELOS_SDK_PATH=auto`** so melos uses PATH's pinned Flutter — never locally, it silently runs whatever Flutter is globally installed. Dart tooling only, no `just` or shell scripts beyond the git hook stub in `tool/hooks/`. **CI**: GitHub Actions (`.github/workflows/*.yml`) on **GitHub-hosted `ubuntu-24.04` runners** (one literal `runs-on:` value repeated per file so a provider swap is a one-line change; no secrets, no self-hosted runner; what the workflows install is listed in `.github/RUNNER.md`). Six workflows: `ci` (the quick checks `format` `analyze` `test` `map-check` `licence-check` `changelog-check` `phrase-check` `branch-lint` `lint-history` as named steps of one job with one setup, each `if: !cancelled()` so one failure never hides the others; `docs-check` and `check-generated` are not `ci` steps — `docs-check` is its own workflow, `gen-fresh-check` covers `check-generated`, and both melos scripts work locally), plus `docs-check` (own job: dartdoc with link validation over every package, the slowest quick check, so it runs in parallel with `ci`), `gen-fresh-check` (own cold job, no caches: regenerates everything from a clean clone and compares it with HEAD), `build-linux`, `web-smoke` (also covers the website build), `release-artifacts`. **Triggers**: `pull_request`, and `push` only to `development`/`production` — a PR-branch push never runs twice; `concurrency` cancels a superseded PR run. `.github/actions/setup` installs the pinned, sha256-verified Flutter tarball into `$RUNNER_TOOL_CACHE` (with `MELOS_SDK_PATH=auto`, as above); hosted runners start clean, so `actions/cache` covers only the build_runner snapshots checkout wipes; verification only, no deployment. **No check is configured as a required status check by the template** (a clone turns on branch protection itself): `tooling:finish` refuses unchecked criteria and re-verifies on merged `development` before closing.

## Branches and issues

Two long-lived branches: `production` (releasable) and `development` (integration, default). Both are merge-only — never push to either directly. Every working branch is `<family>/<N>-<slug>`
(`N` = GitHub issue number), one of exactly six families: `feature/` `bugfix/` `chore/` `documentation/` `release/` (branch from `development`) or `hotfix/` (branch from `production`).

Every working branch lives in its own worktree at `.worktrees/<N>/`, created with `git worktree add --relative-paths`. The main checkout stays parked on `development`.
**`git stash` is forbidden** — use a worktree or a WIP commit instead. Rebase freely before a PR
exists; once a PR is open, only `git merge development` into the branch (no rebase). Workflow
tooling (`core/tooling/tooling`, `fvm dart run tooling:<cmd>`, main checkout only): `branch_new <family> <N> <slug>` builds the worktree and labels the issue; `finish <N>` plain-merges the PR (refusing on unchecked criteria), then verifies the check suite against merged `development` before closing it — a failing check relabels `status/in-progress` instead; `branch_lint` audits names.

1 PR = 1 issue. PR title is a conforming commit subject ending `(#N)`; body carries the issue's
acceptance-criteria checklist. A reviewer (human, or an agent the maintainer has explicitly delegated to) reviews before merge; **plain merge only** (the merge template
makes the PR title the merge-commit subject — never squash, never rebase-merge). Issue labels move
`status/in-progress` → `status/review`; closed explicitly once verified on merged `development`.

## Commits

`type(scope): description (#N)` — type and scope both required, type one of `feat fix docs style refactor perf test build ci chore revert merge release`. No exemption for merge, release or fixup/squash commits: `merge(<scope>): <branch> into <target> (#N)`, `release(<pkg>): X.Y.Z (#N)`.

Enforced locally by `tool/hooks/commit-msg` after `melos run hooks`; re-checked over history by `fvm dart run tooling:lint_history`. Grandfathered non-conforming commits are exempted **by SHA only**, in `tool/commit-baseline.txt` — never by pattern.

## Workspace layout

`core/<category>/<package>` — the template's own packages, grouped by what they are: `architecture/` (`mvc` triad + nav/launcher/dialog services, `mvc_lints` — not a workspace member), `contracts/` (`auth`/`data`/`teams` backend-agnostic interfaces — `teams` is team tenancy and is optional for a single-user app, `jobs` is the leased background-job queue, `legal_facts` — the one placeholder-legal-facts source `apps/app`'s `AppConfig` and `apps/website` both read), `design/` (`ui` — `AppTheme` + naked_ui/mix — and `tokens_builder`, which builds it from `ui/tokens/*.json`), `tooling/tooling` (`commit_msg`, `lint_history`, `map`, `rename`, …).

`backend/<provider>/` — one directory per backend integration; only `appwrite/` here (`tool` = package `appwrite_tool`, provisioning/deploy; `adapters` = `appwrite_adapters`, `melos run test:integration:backend_appwrite`; `schema` = `appwrite_schema`; plus `functions/`) — a clone wiring up a second provider adds its own `backend/<provider>/` sibling, never inside `appwrite/`.

`packages/` — clone-owned or optional packages, outside the template's required skeleton: just `domain` here (models shared by `apps/app` and `backend/appwrite/functions/`) — a clone's own feature packages join it too. `apps/app` — `lib/app/` (DI, routes, `AppConfig`), `lib/i18n/`, `lib/features/<f>/` (MVC triads, nested by route: `legal/` holds `document/` and `licences/`, `settings/` holds `account/`, `privacy/` and `paywall/`; helper widgets in each feature's `widgets/`), `lib/shared/widgets/` (widgets shared by top-level features). `apps/website` — the Jaspr landing page, no Flutter dependency. `docs/map.md` is generated, never hand-edit.

**Licence and release boundaries**: **Apache-2.0 + CLA** (this template's own default — `LICENSE`/`NOTICE`/`CONTRIBUTING.md`/`CLA.md`/`SECURITY.md` at root, every identifying field in them sourced from `core/contracts/legal_facts`' placeholder entity, not data about any real maintaining organisation — see the root `README.md`'s "After cloning" checklist; every workspace member + `mvc_lints` needs its own `CHANGELOG.md`, enforced by `melos run changelog-check`). **Web** is the only release platform: CI builds `apps/website` and compiles `apps/app` for Linux (`build-linux`, a compile check only); `apps/app`'s web build gets an in-browser boot smoke test (`web-smoke`) — Android/iOS release signing is per-clone setup, never done by the template (the debug-signed release config in `apps/app/android/app/build.gradle.kts` is `flutter create`'s default, left as-is on purpose). Push notifications are **pre-prompt only** (`apps/app/lib/features/permission_pre_prompt/`) — no FCM/APNs/Appwrite Messaging delivery is wired; a clone adds its own per platform.
